# Supplier portal API (starter lab)

A gentle first CyberCTF lab: no vulnerability. You learn to read a small REST
API's docs and make an authenticated request.

**Task:** report the amount of invoice `INV-20507` from the portal API.

## Run it

The lab is described once in [`isoloom.yml`](isoloom.yml) ([Isoloom](https://www.isoloom.com)):
Isoloom translates that one description to every target, containers or one VM per machine, on
this machine, a server or a cloud. Nothing is written per target. Generate, then run with Docker:

```bash
isoloom generate
docker compose -f .isoloom/docker/compose.yml up -d --build --wait
```

With VMs (VirtualBox, VMware, Parallels, libvirt): `cd .isoloom/vagrant && vagrant up`.
`.isoloom/` is build output: regenerate it after changing `isoloom.yml`, never edit it.

Open http://localhost:8080 for the API docs, then:

```bash
curl -H "X-Portal-Key: vendor-demo-key" http://localhost:8080/api/invoices/INV-20507
```

The `amount` field is your evidence. Without the CyberCTF launcher the lab uses
its public development value; launched from CyberCTF you get your own value.

## Layout
- `isoloom.yml` , the lab: machines, network, inputs, checks. The database is the Isoloom
  catalogue's MySQL (port, users and schema set in its `with:`); the API is portable steps on
  Debian 12 with its command, environment and healthcheck
- `build/web/src/` , the Flask API (`app.py`, its template and requirements)
- `build/database/init/` , the schema and seed rows, loaded at the database's first start
- `build/database/*evidence.sh` , the evidence claim and placement (the database's `setup`)
- `build/check/check.sh` , the lab is still solvable (run from the player's side)
- `.isoloom/` , generated by `isoloom generate` (Compose, Vagrant, Terraform), don't edit
- `tests/` , pytest suite (runs against `.isoloom/docker/compose.yml`, `APP_BASE_URL=http://localhost:8080`)
